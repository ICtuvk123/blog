Tokenization

Before a language model can assign probabilities to text, the text has to be turned into something the model can actually operate on. Raw text usually starts as a Unicode string:

string = "Hello, 🌍! 你好!"

The model, however, works over sequences of tokens, and those tokens are usually represented internally as integer indices:

indices = [15496, 11, 995, 0]

This is the role of tokenization. It builds the interface between human-readable text and the model's token sequence. At minimum, a tokenizer needs two directions: encode, which converts a string into tokens or token indices, and decode, which converts those tokens back into text. A Tokenizer class is mainly the object that implements these two transformations.

What GPT Tokenization Reveals

If we inspect a GPT tokenizer from OpenAI, such as tiktoken, the first thing we notice is that tokens do not always match our intuitive idea of words.

tokenizer = get_gpt5_tokenizer()
string = "Hello, 🌍! 你好!"

For example, a word and the space before it are often merged into the same token, such as " world". This means the same visible word can have different token representations depending on where it appears. In "hello hello", the first hello and the second hello may be tokenized differently because the second one includes the preceding space.

Numbers show a similar pattern. They are often split into chunks of a few digits rather than treated as a single semantic unit. So a tokenizer is closer to a statistical compression mechanism than a dictionary of words. It cuts text into pieces that are convenient for the model to represent and learn from.

Why Compression Ratio Matters

Once tokens become the sequence seen by the model, the number of tokens matters directly. We can describe this with compression ratio: how many bytes of raw text are represented by each token.

compression_ratio = get_compression_ratio(string, indices)

A larger compression ratio means the same text becomes a shorter token sequence. This matters because attention cost grows roughly quadratically with sequence length. If a tokenizer breaks text into too many pieces, the model pays more attention cost for the same underlying content.

One natural response is to increase the vocabulary size:

vocabulary_size = tokenizer.n_vocab

A larger vocabulary can improve compression because more common patterns can be represented by single tokens. The tradeoff is sparsity. When there are more possible token values, each individual token may appear less often in training, so the model gets fewer examples from which to learn its behavior. Tokenizer design is therefore balancing two pressures: compress the sequence, while keeping token learning dense enough.

The Limits of Word-Based Tokenization

The most direct idea is to tokenize by words. This quickly runs into several problems.

Many words are rare, so the model may see too few examples to learn them well. A word-level vocabulary also does not naturally give us a fixed vocabulary size, because new words keep appearing as the corpus grows. When an unseen word appears at test time, the tokenizer needs a special UNK token, which throws away information and can make downstream computation awkward.

This suggests the kind of tokenizer we want. It should have a fixed vocabulary, represent arbitrary text, shorten common patterns, and still handle rare patterns without collapsing them into an unknown symbol.

Byte Pair Encoding

Byte Pair Encoding, or BPE, was introduced by Philip Gage in 1994 for data compression. It was later adapted to NLP for neural machine translation by Sennrich et al. in 2015. Earlier NLP work often used word-based tokenization, while GPT-2 later popularized BPE-style tokenization for language models.

The core idea is simple: train the tokenizer on raw text, and let the vocabulary adapt to the data. Common byte sequences become single tokens. Rare byte sequences remain represented by smaller pieces. The common cases become shorter, and the rare cases remain expressible.

The training procedure can be understood as:

  1. Start with each byte as a token.
  2. Count adjacent token pairs in the training text.
  3. Merge the most common adjacent pair into a new token.
  4. Repeat until the desired vocabulary size is reached.

This gives BPE an important property. The vocabulary size is fixed, yet arbitrary text can still be represented, because the tokenizer can always fall back to byte-level pieces. In this sense, BPE is a practical compromise between word-level tokenization and pure byte-level tokenization.

Key Takeaways

Tokenization decides how raw text becomes the sequence that a model actually sees. This affects context length, attention cost, vocabulary size, and the sparsity of token learning. Larger vocabularies can compress text better, but they can also make individual tokens harder to learn from data.

BPE is useful because it gives common patterns short representations while keeping rare patterns representable. From this point of view, the tokenizer is not just a preprocessing detail. It shapes the model's view of the text before the model begins learning anything from it.
