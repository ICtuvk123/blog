Resource Accounting

When training large models, it is easy to focus only on the model architecture and treat the system underneath as something vague. But parameters, gradients, activations, optimizer states, compute, bandwidth, and communication all have concrete costs.

The main mindset is resource accounting. For a training run, we want to know where memory is spent, where FLOPs are spent, when bandwidth becomes the bottleneck, and how these quantities interact. There is no special mystery in this part of machine learning; it is mostly careful bookkeeping.

Tensor Memory and Floating-Point Types

Almost everything in training is stored as floating-point tensors: parameters, gradients, activations, and optimizer states. So the first question is simple: how many bytes does each value use?

float32 / fp32

float32, also called single precision, is the traditional baseline. It has 32 bits: 1 sign bit, 8 exponent bits, and 23 fraction bits. In PyTorch, torch.float32 uses 4 bytes per value.

x = torch.zeros(4, 8)

assert x.numel() == 4 * 8
assert x.element_size() == 4
assert get_memory_usage(x) == 4 * 8 * 4  # 128 bytes

This small example is easy to reason about, but the same calculation becomes large very quickly. One matrix in the feedforward layer of GPT-3 already takes about 2.3 GB:

assert get_memory_usage(torch.empty(12288 * 4, 12288)) == 2304 * 1024 * 1024
# about 2.3 GB

This is one reason lower precision matters in deep learning. It is not only about faster arithmetic; memory capacity and memory movement become constraints by themselves.

float16 / fp16

float16, or half precision, cuts memory in half. It has 16 bits: 1 sign bit, 5 exponent bits, and 10 fraction bits. In PyTorch, each value uses 2 bytes.

x = torch.zeros(4, 8, dtype=torch.float16)
assert x.element_size() == 2

The benefit is immediate: the same number of tensor values uses half the memory. The problem is dynamic range. Small values can underflow:

x = torch.tensor([1e-8], dtype=torch.float16)
assert x == 0  # underflow

During training, this kind of underflow can become a stability problem rather than just a representation detail.

bfloat16

bfloat16 was developed to keep the memory benefit of fp16 while improving dynamic range. It still uses 2 bytes per value, but it keeps the same exponent width as fp32. The cost is fewer fraction bits, so the resolution is worse.

For deep learning, this tradeoff is often acceptable. Training is usually more sensitive to range than to having many precise fraction bits.

x = torch.tensor([1e-8], dtype=torch.bfloat16)
assert x != 0  # no underflow

fp8, fp4, and Lower Precision

fp8 was standardized in 2022 for machine-learning workloads. H100 GPUs support two common variants:

  • E4M3: range approximately [-448, 448].
  • E5M2: range approximately [-57344, 57344].

The slide reference is Micikevicius et al. 2022.

NVIDIA later introduced nvfp4 in 2025. It uses only 4 bits per value, with representable values such as:

-6, -4, -3, -2, -1.5, -1.0, -0.5, 0.0, 0.5, 1.0, 1.5, 2, 3, 4, 6

Since 4 bits is extremely limited, nvfp4 uses a separate scale factor per block. The slide also notes that Nemotron 3 Super was trained in NVFP4. The broader point is that numeric format has become part of training-system design.

GPU Resource Model

After understanding how tensors occupy memory, the next question is where that memory lives and how data moves. A simple GPU system has CPU and RAM on the host side, GPU DRAM on the device side, streaming multiprocessors on the GPU, and a PCI bus connecting host and device.

PyTorch exposes basic CUDA inspection:

if not torch.cuda.is_available():
    return

num_gpus = torch.cuda.device_count()

for i in range(num_gpus):
    properties = torch.cuda.get_device_properties(i)

This matters because computation and data movement are separate resources. Later, when discussing bandwidth and arithmetic intensity, we will use this view to decide whether an operation is limited by math or by memory movement.

Einops

Before doing resource accounting, it helps to write tensor dimensions clearly. Many PyTorch operations are straightforward mechanically; the difficult part is often remembering which dimension means what. einops and einsum make this bookkeeping explicit.

einsum

einsum is generalized matrix multiplication with named dimensions. For ordinary matrix multiplication:

x = torch.ones(3, 4)  # seq1 hidden
y = torch.ones(4, 3)  # hidden seq2

# Old way
z = x @ y  # seq1 seq2

# Einops way
z = einsum(x, y, "seq1 hidden, hidden seq2 -> seq1 seq2")

The hidden dimension appears in the inputs and disappears from the output, so it is summed over. The expression is longer than x @ y, but it makes the dimension contract explicit.

For a batched example:

x = torch.ones(2, 3, 4)  # batch seq1 hidden
y = torch.ones(2, 3, 4)  # batch seq2 hidden

# Old way
z = x @ y.transpose(-2, -1)  # batch seq1 seq2

# Einops way
z = einsum(x, y, "batch seq1 hidden, batch seq2 hidden -> batch seq1 seq2")

We can also use ... for any number of leading broadcast dimensions:

z = einsum(x, y, "... seq1 hidden, ... seq2 hidden -> ... seq1 seq2")

reduce

reduce applies an operation over dimensions that disappear from the output pattern.

x = torch.ones(2, 3, 4)  # batch seq hidden

# Old way
y = x.sum(dim=-1)

# Einops way
y = reduce(x, "... hidden -> ...", "sum")

The operation can be sum, mean, max, or min. Again, the advantage is that the dimension change is written directly in the expression.

rearrange

rearrange is useful when one dimension is really a flattened combination of several dimensions. For example, total_hidden might represent heads * hidden1:

x = torch.ones(3, 8)  # seq total_hidden
w = torch.ones(4, 4)  # hidden1 hidden2

x = rearrange(x, "... (heads hidden1) -> ... heads hidden1", heads=2)
x = einsum(x, w, "... hidden1, hidden1 hidden2 -> ... hidden2")

This looks like a notation convenience, but it also helps resource accounting. If we do not know what each dimension means, we cannot reliably count memory, FLOPs, or communication.

Compute Accounting

Now we can count computation. Two similar terms need to be separated:

  • FLOPs: floating-point operations, the total amount of computation.
  • FLOP/s: floating-point operations per second, the rate at which hardware performs computation.

The slides estimate GPT-3 training at 3.14e23 FLOPs and speculate GPT-4 training at 2e25 FLOPs. H100 peak performance is listed as 1979 teraFLOP/s with sparsity, and roughly half of that without sparsity.

A rough upper-bound estimate for total compute is:

h100_flop_per_sec = 1979e12 / 2
total_flops = num_gpus * seconds * h100_flop_per_sec

This is only a ceiling. Real training reaches some fraction of it depending on the workload and implementation.

Counting Matmul FLOPs

For matrix multiplication y = x @ w:

if torch.cuda.is_available():
    B = 16384  # number of points
    D = 32768  # dimension
    K = 8192   # number of outputs
else:
    B = 1024
    D = 256
    K = 64

x = torch.ones(B, D, device=cuda_if_available())
w = torch.randn(D, K, device=cuda_if_available())
y = x @ w

Each output element is a dot product over the D dimension. For each (i, j, k) triple, there is one multiplication and one addition, so:

actual_num_flops = 2 * B * D * K

This is why matrix multiplication dominates large model training. It is regular, dense, and extremely compute-heavy at scale.

Model FLOPs Utilization

Peak FLOP/s depends strongly on dtype, so utilization should be compared against the hardware number for the relevant dtype:

promised_flop_per_sec = get_promised_flop_per_sec(x.dtype)
mfu = actual_flop_per_sec / promised_flop_per_sec

MFU means model FLOPs utilization:

MFU = actual FLOP/s / promised FLOP/s

An MFU >= 0.5 is usually quite good. It tends to be higher when matrix multiplications dominate, because large matmuls are easier to run near the hardware's compute capacity.

Bandwidth, Arithmetic Intensity, and Bottlenecks

FLOPs alone do not determine runtime. Some operations do little computation but move a lot of data. In those cases, memory bandwidth rather than arithmetic throughput becomes the limiting resource.

Communication vs Computation Time

Consider ReLU:

n = 1024 * 1024
x = torch.ones(n, dtype=torch.bfloat16, device=cuda_if_available())
y = torch.relu(x)

bytes = (2 * n) + (2 * n)  # read x, write y; bf16 is 2 bytes/value
flops = n                 # n comparisons

communication_time = bytes / h100_bytes_per_sec
computation_time = flops / h100_flop_per_sec
total_time = max(communication_time, computation_time)

This assumes communication and computation overlap perfectly, so the slower side determines total time. ReLU does very little math per element, yet it still needs to read and write memory, which makes it bandwidth-sensitive.

Arithmetic Intensity

Arithmetic intensity makes this bottleneck more systematic:

accelerator_intensity = hardware FLOP/s / hardware bytes/s
arithmetic_intensity = workload FLOPs / workload bytes

The rule is:

  • Memory-bound if arithmetic_intensity < accelerator_intensity.
  • Compute-bound if arithmetic_intensity > accelerator_intensity.

For ReLU:

arithmetic_intensity = 0.25
h100_accelerator_intensity ~= 295.37

This is far below H100's accelerator intensity, so ReLU is memory-bound.

GELU performs more computation:

n = 1024
x = torch.ones(n, dtype=torch.bfloat16, device=cuda_if_available())
y = F.gelu(x)

bytes = (2 * n) + (2 * n)  # read x, write y
flops = 20 * n             # approximate cost of GELU

Its arithmetic intensity is about 5, which is still below the H100 threshold, so GELU is also memory-bound.

Matrix multiplication behaves differently:

n = 1024
x = torch.ones(n, n, dtype=torch.bfloat16, device=cuda_if_available())
w = torch.ones(n, n, dtype=torch.bfloat16, device=cuda_if_available())
y = x @ w

bytes = (2 * n * n) + (2 * n * n) + (2 * n * n)  # read x, read w, write y
flops = n * n * (2 * n - 1)                      # n^2 dot products
arithmetic_intensity = flops / bytes             # approximately n / 3

As n grows, the arithmetic intensity of matmul grows as well. Large matrix multiplications can therefore become compute-bound, which is one reason accelerators are designed to make this operation extremely fast.

Roofline Intuition

The roofline plot connects arithmetic intensity with realized FLOP/s. The x-axis is arithmetic intensity, and the y-axis is realized FLOP/s. The sloped region corresponds to bandwidth-bound workloads, while the flat region corresponds to compute-bound workloads.

The useful intuition is that an algorithm doing little computation per byte moved cannot reach peak FLOP/s, no matter how fast the arithmetic units are. To approach peak compute, the workload needs enough arithmetic intensity.

Memory Accounting

For a rough transformer-like model with dimension D, batch-related size B, and L layers, we can estimate:

# Parameters, assuming bf16
parameter_memory = 2 * (D * D * L)

# Activations, assuming bf16
activation_memory = 2 * B * D * L

# Gradients
gradient_memory = 2 * parameter_memory

# Optimizer states, commonly fp32 for stability
optimizer_state_memory = 4 * parameter_memory

Optimizer states are easy to underestimate. Adam stores first and second moments, and these are often kept in fp32 for stability. Together, the two moments are about 8 bytes per parameter, which can become a major part of training memory.

Activation Checkpointing

When activation memory becomes too large, activation checkpointing trades compute for memory. The forward pass stores only selected activations. During the backward pass, missing activations are recomputed from the nearest checkpoint.

Without checkpointing, we might store every intermediate value:

x g1 h1 g2 h2 g3 h3 g4 h4

With checkpointing, we store fewer values:

x h1 h2 h3 h4

We can measure the peak memory of a checkpointed model like this:

model = DeepNetworkCheckpointed(dim=D, num_layers=L).to(cuda_if_available())
checkpointed_memory = get_max_memory_usage(lambda: model(x).backward())

For very deep networks, it is also possible to store only some layer outputs:

store all layers:  | h1 h2 h3 h4 h5 h6 h7 h8 h9 |
store no layers:   |                            |
store some layers: |       h3       h6       h9 |

This reduces peak activation memory further, at the cost of recomputation during backpropagation. That is the recurring theme of resource accounting: training cost is distributed across dtype, parameters, activations, optimizer state, compute, bandwidth, and the tradeoffs we choose between memory and recomputation.
